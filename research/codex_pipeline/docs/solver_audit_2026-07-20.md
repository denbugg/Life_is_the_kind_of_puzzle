Дата проверки: 20 июля 2026 года  
Проверенный файл: `pazzle_full_puzzle_solver.py`, 658 строк

## Резюме

Синтаксис корректен: `python -m py_compile` завершается без ошибок. Базовые smoke-тесты архитектур также проходят:

- `EdgeMatcher`: `(2, 7, 20, 20) -> (2, 1)`;
- `PositionPrior`: `(2, 3, 20, 20) -> (2, 24)` для row и column;
- `TinyCondUNet`: `(2, 3, 20, 20) -> (2, 3, 20, 20)`;
- `SwapActorCritic`: `(1, 4, 38) -> logits (1, 4), value (1,)`.

При этом найдены ошибки, способные ухудшать решение, выбирать неправильные модели или формировать некорректный submission. Самые опасные:

1. `optimize_layout()` не сохраняет настоящий лучший расклад и способен вернуть результат хуже входного.
2. `solve_test()` не очищает каталог submission и добавляет в ZIP устаревшие PNG от прошлых запусков.
3. RL-этап оптимизирует другую целевую функцию, но безусловно заменяет baseline-расклад; отрицательный результат validation нигде не учитывается.
4. RL-checkpoint жёстко зафиксирован как `epoch1` и выбирается не как последний.
5. Поиск данных и checkpoint-файлов неоднозначен при нескольких Kaggle datasets и может смешать модели разных запусков.
6. Пустой test-набор не считается ошибкой: код может создать пустой ZIP либо упаковать только старые файлы.

## Подробное описание

### OPT-001 — оптимизатор способен вернуть расклад хуже входного

**Строки:** 327–352.

`best_total` инициализируется как `-inf`, а objective исходного `layout` не сохраняется. Полный objective проверяется только раз в 5000 шагов и после цикла:

```python
best = layout.copy()
best_total = -np.inf
...
if step % 5000 == 0:
    total = layout_objective(...)
    ...
```

Проверка на `step == 0` выполняется уже **после первого принятого/отклонённого swap**, а не для исходного состояния. Между контрольными точками хороший расклад также может быть найден и затем потерян.

**Воспроизведение:** на синтетической сетке `2x2`, при `SWAP_STEPS=1` и `seed=0`:

```text
initial layout: [0, 1, 2, 3]
initial objective: 0.00400000019
returned layout: [3, 1, 2, 0]
returned objective: 0.00200000009
```

То есть функция вернула objective примерно в два раза хуже входного.

**Последствия:** нестабильное качество, особенно при высокой температуре simulated annealing; увеличение `SWAP_STEPS` не гарантирует монотонного улучшения возвращаемого результата.

**Исправление:**

1. Сразу вычислить objective исходного расклада.
2. Поддерживать `current_total` через точную локальную дельту `after - before`.
3. Обновлять `best` после каждого принятого swap, а не раз в 5000 шагов.

Пример логики:

```python
current_total = layout_objective(layout, right, down, pos_score)
best_total = current_total
best = layout.copy()

...
delta = after - before
accepted = delta >= 0 or rng.random() < np.exp(delta / temperature)
if accepted:
    current_total += delta
    if current_total > best_total:
        best_total = current_total
        best = layout.copy()
else:
    layout[a], layout[b] = layout[b], layout[a]

return best
```

Периодический полный пересчёт можно оставить только как assertion против накопленной численной погрешности.

### OUT-001 — submission содержит файлы от предыдущих запусков

**Строки:** 627–641.

Каталог создаётся с `exist_ok=True`, но не очищается. Затем в ZIP добавляются **все** PNG, которые находятся в каталоге:

```python
pred_dir.mkdir(parents=True, exist_ok=True)
...
for path in sorted(pred_dir.glob("*.png")):
    zf.write(path, arcname=path.name)
```

**Воспроизведение:** при одном текущем test-файле `current.png` и заранее существующем `submission/stale.png` архив содержит:

```text
['current.png', 'stale.png']
```

При этом лог сообщает `files=1`, то есть количество обработанных test-файлов, а не реальное число элементов ZIP.

**Последствия:** лишние или устаревшие предсказания, потенциально невалидный Kaggle submission, несоответствие логов фактическому архиву.

**Исправление:** очищать каталог перед запуском либо, надёжнее, сохранять список файлов, созданных именно текущим запуском, и упаковывать только его. Для защиты от частично сформированного архива использовать временный каталог и временный ZIP с последующим atomic rename.

### RL-001 — RL безусловно заменяет baseline, хотя использует другую целевую функцию

**Строки:** 371–377, 428–429, 441–452, 561–566, 591–600, 603–624.

Baseline использует:

- `compatibility_scores()`: raw seam score плюс logits обученного `EdgeMatcher`;
- позиционный вес `POSITION_WEIGHT`, по умолчанию `0.12`.

RL-refiner заново строит матрицы только по raw pixel seam через `rl_visual_matrices()` и использует жёстко заданный вес `0.15` в трёх местах. Поэтому `best_board` в RL является лучшим только по **другой** метрике.

После RL нет проверки baseline objective:

```python
layout, rl_objective = refine_layout_rl(...)
return assemble(clean_tiles, layout), ...
```

Даже если validation показывает отрицательный `delta`, `main()` всё равно запускает test с тем же RL-моделем.

**Последствия:** RL может разрушить полезные решения EdgeMatcher и снизить SSIM, оставаясь «лучше» по собственной seam-only метрике.

**Исправление:** минимум — после RL вычислять оба layout по baseline objective и принимать RL-кандидат только при неухудшении:

```python
baseline_value = layout_objective(baseline_layout, right, down, pos)
rl_value = layout_objective(rl_layout, right, down, pos)
layout = rl_layout if rl_value >= baseline_value else baseline_layout
```

Предпочтительно передавать RL ту же совместимость и тот же позиционный вес либо обучать policy под ровно тот objective, который используется на inference. Validation должен возвращать метрики и автоматически отключать RL при статистически устойчивом отрицательном эффекте.

### CKPT-001 — RL-checkpoint жёстко зафиксирован как `epoch1`

**Строки:** 180–185.

```python
pattern = "rl_swap_actor_critic_epoch1.pt"
...
return files[0]
```

Код:

- не ищет `epoch*.pt`;
- не выбирает максимальный epoch;
- возвращает первый путь в неявном порядке;
- падает, если присутствует только более новый checkpoint.

**Воспроизведение:** наличие только `models/rl_swap_actor_critic_epoch2.pt` приводит к:

```text
FileNotFoundError: RL checkpoint not found: rl_swap_actor_critic_epoch1.pt
```

**Исправление:** использовать общий resolver `epoch*.pt`, выбирать максимальный корректно разобранный epoch и ограничивать поиск явным `MODEL_DIR`.

### CKPT-002 — checkpoint-файлы и dataset могут быть выбраны из разных Kaggle inputs

**Строки:** 168–192, 195–221.

`find_latest()` рекурсивно собирает совпадения из всего `/kaggle/input`, а каждый тип модели выбирается независимо. `find_data_root()` возвращает первый найденный dataset. При нескольких подключённых Kaggle datasets возможен набор вида:

- EdgeMatcher из эксперимента A;
- PositionPrior из эксперимента B;
- denoiser из эксперимента C;
- train/test data из эксперимента D.

Никакого общего run ID, model root, manifest, grid/tile contract или dataset fingerprint не проверяется.

Дополнительно локальный поиск в `find_latest()` использует только `Path(".").glob(...)`, то есть не рекурсивен и зависит от текущего рабочего каталога, а не от расположения скрипта.

**Последствия:** тихая загрузка логически несовместимого ансамбля либо трудно диагностируемые ошибки `load_state_dict`.

**Исправление:** ввести обязательные `MODEL_DIR` и `DATA_ROOT`; хранить рядом manifest с версиями всех компонентов, размером сетки, размером tile, feature schema и diffusion config; запрещать смешивание checkpoint-файлов из разных корней.

### DATA-001 — отсутствие test-файлов не считается ошибкой

**Строки:** 627–641.

Код проверяет только `data_root / "test" / "*.png"`. Если файлы расположены в `test/inputs`, путь неверен. Если test-каталог пуст или не найден, код всё равно создаёт ZIP и печатает `files=0`.

В сочетании с OUT-001 архив может состоять исключительно из старых предсказаний.

**Исправление:**

- явно определить layout dataset;
- при необходимости поддержать `test/inputs`;
- перед inference выполнить `if not files: raise FileNotFoundError(...)`;
- после формирования архива проверить точное равенство имён ZIP и текущих test-файлов.

### RL-002 — заявленные отдельные local-features фактически дублируются

**Строки:** 51–60, 488–540.

Контракт объявляет четыре разных признака:

```text
a_local_before, b_local_before, a_local_after, b_local_after
```

Но implementation записывает один и тот же объединённый score рёбер вокруг обеих позиций дважды:

```python
np.tanh(s["before_visual"] / 8), np.tanh(s["before_visual"] / 8),
np.tanh(s["after_visual"] / 8), np.tanh(s["after_visual"] / 8),
```

`before_visual`/`after_visual` рассчитаны по union рёбер `neighbors(a) | neighbors(b)`, а не отдельно для `a` и `b`.

Проверка `feature_names` в checkpoint этого не обнаруживает: имена совпадут, даже если семантика значений ошибочна.

**Последствия:** policy не получает заявленную асимметричную информацию о качестве позиций `a` и `b`; при несовпадении с training-кодом вход policy полностью нарушен.

**Исправление:** сверить training feature builder. Рассчитать `a_local_*` и `b_local_*` отдельно, а в checkpoint хранить `feature_schema_version` и все коэффициенты нормализации, а не только список имён.

### IO-001 — неверная геометрия изображения может быть молча принята

**Строки:** 243–245.

`load_tiles()` сразу выполняет reshape, не проверяя исходный `image.shape`. Проверяется лишь общее число элементов. Поэтому изображение `240x960x3`, имеющее столько же пикселей, сколько `480x480x3`, принимается без ошибки и преобразуется в `(576, 20, 20, 3)` с неверной геометрией.

**Воспроизведение:**

```text
input_shape=(240, 960, 3)
accepted_tiles_shape=(576, 20, 20, 3)
```

**Исправление:** до reshape проверять точное равенство:

```python
expected = (GRID * TILE, GRID * TILE, 3)
if image.shape != expected:
    raise ValueError(f"Expected image shape {expected}, got {image.shape}: {path}")
```

Также полезно проверять, что `layout` является перестановкой `0..N-1` перед `assemble()`.

### CFG-001 — отсутствует централизованная валидация параметров

**Строки:** 36–49 и места использования параметров.

Конкретные отказы:

- `EDGE_TOPK=0` приводит к `ValueError: torch.cat(): expected a non-empty list of Tensors` на строке 296;
- `EDGE_BATCH<=0` ломает `Tensor.split()` или `range()`;
- `timesteps<=0` создаёт пустой beta schedule и ошибку индексации;
- отрицательный `VALIDATE_IMAGES` имеет неожиданную семантику slice;
- `VALIDATE_IMAGES=0` или пустой train inputs приводит к `np.mean([])` и `NaN` в логах;
- `SWAP_STEPS`, `RL_STEPS`, `RL_STAGNATION`, веса и blend допускают бессмысленные или нечисловые значения без понятной диагностики.

**Исправление:** одна функция `validate_config()` в начале `main()` с диапазонами, `math.isfinite()` и сообщениями, содержащими имя переменной и полученное значение.

### RL-003 — `RL_PROPOSALS=1` создаёт `NaN`

**Строки:** 557–566.

`torch.std()` по умолчанию использует correction/Bessel correction. Для одного элемента standard deviation равна `NaN`; `clamp_min()` не исправляет `NaN`:

```text
std_default = nan
normalized heuristic = [nan]
```

**Исправление:** либо требовать `RL_PROPOSALS >= 2`, либо использовать:

```python
std = heuristic.std(correction=0)
heuristic = (heuristic - heuristic.mean()) / std.clamp_min(1e-6)
```

### RL-004 — некорректный `RL_PROPOSALS` может привести к падению или бесконечному циклу

**Строки:** 455–486, 557–566.

- При `k=0` возвращается пустой массив неправильной для модели формы, после чего actor/value path падает.
- Максимум уникальных неупорядоченных пар равен `N * (N - 1) / 2 = 165600` для `N=576`.
- При `k > 165600` условие `while len(pairs) < k` невозможно выполнить: цикл бесконечен.
- При значениях, близких к максимуму, случайный поиск уникальных пар резко замедляется из-за большого числа повторов.

**Исправление:** валидировать `1 <= k <= max_pairs`; для больших `k` генерировать пары детерминированно или без replacement из пространства индексов.

### SWAP-001 — генерация «локальных» swaps нарушает геометрию сетки

**Строки:** 331–339.

Позиции представлены плоскими индексами, к которым прибавляются `1`, `GRID`, `GRID±1`. Границы строк не проверяются. Например, `23 + 1 = 24` интерпретируется как соседний swap, хотя это переход из `(row=0, col=23)` в `(row=1, col=0)` с Manhattan distance 24. `np.clip()` дополнительно создаёт сильное смещение на позициях `0` и `N-1` и много `a == b`.

**Последствия:** хуже исследуется пространство раскладов, особенно у границ; вероятности предложений не соответствуют предполагаемым соседям/диагоналям.

**Исправление:** выбирать `(dr, dc)` и проверять координаты до обратного преобразования в flat index.

### MODEL-001 — checkpoint contract неполный

**Строки:** 64–165, 195–221, 225–240.

- `EdgeMatcher(base=64)` и `PositionPrior(base=48)` создаются с hardcoded width.
- `SwapActorCritic(hidden=256)` создаётся с hardcoded hidden size.
- Для denoiser читается `base_channels`, но не `time_dim`.
- Diffusion beta schedule всегда заново строится как linear `1e-4..2e-2`; schedule type и границы из training config не загружаются и не проверяются.
- RL contract проверяет только список имён, но не коэффициенты `0.15`, `/4`, `/8`, missing value `-4`, progress horizon и другие semantic parameters.

**Последствия:** часть несовпадений даст явный `load_state_dict` error, но несовпадение diffusion schedule или feature scaling может тихо снижать качество.

**Исправление:** хранить полный versioned config/manifest и валидировать его до загрузки весов. Для denoiser использовать тот же schedule, что при training.

### MEM-001 — загрузка checkpoint прямо на GPU создаёт лишний пик памяти

**Строки:** 195–220.

Модели сначала размещаются на `DEVICE`, затем `torch.load(..., map_location=DEVICE)` создаёт ещё одну копию state dict на GPU. Для denoiser checkpoint-словарь остаётся жив до конца `load_models()`, пока уже существуют все загруженные модели.

**Последствия:** необязательный CUDA OOM во время старта, хотя сами модели могли бы помещаться после освобождения checkpoint tensors.

**Исправление:** загружать checkpoint на CPU, создавать/заполнять модель на CPU, удалять state dict, затем переносить модель на GPU. При возможности использовать безопасный weights-only режим и явно доверенный model directory.

### VAL-001 — validation недостаточен и не влияет на решение

**Строки:** 603–624, 644–654.

- По умолчанию используются только первые два файла после лексикографической сортировки.
- Это `train`, а не явно выделенный holdout; если модели обучались на этих примерах, оценка leakage-prone.
- Нет случайной/стратифицированной выборки и доверительного интервала.
- Отрицательный средний RL delta только печатается и не отключает RL для test.
- При пустом списке печатаются `NaN` и выполнение продолжается.

**Исправление:** фиксированный manifest holdout-файлов, достаточный sample size, возврат структурированных метрик из `validate()`, проверка минимального improvement/guardrail и автоматический fallback на baseline.

### EDGE-001 — нейросетевой matcher видит только два raw-seam кандидата

**Строки:** 281–303; default `EDGE_TOPK=2` на строке 40.

Для каждого tile EdgeMatcher вычисляется только для кандидатов, которые уже вошли в top-2 по простому pixel MSE. Если настоящий сосед имеет освещение, текстуру или denoise-артефакт и не попал в top-2, нейросеть никогда не сможет его восстановить; для остальных пар остаётся только raw seam score.

Это не runtime exception, но существенный bottleneck качества.

**Исправление:** измерить recall истинного соседа в top-k на holdout; увеличить `k` до значения с приемлемым recall, использовать union нескольких дешёвых метрик/embeddings либо считать сеть для всех пар chunk-ами, если ресурсы позволяют.

### OBS-001 — диагностические логи неточны

**Строки:** 576, 595–599.

- Лог `steps={RL_STEPS}` выводит настроенный максимум, а не `env.steps`; при early stopping фактическое число шагов меньше.
- Условие `if no_gain > RL_STAGNATION` останавливает на один шаг позже ожидаемого; обычно нужно `>=`.
- При `rl_model is None` переменная и логика validation всё равно называют итог `rl_score`, хотя это baseline.

### REPRO-001 — seed не гарантирует повторяемость на CUDA

**Строки:** 644–648.

Устанавливаются Python/NumPy/PyTorch seeds, но не включаются deterministic algorithms и не фиксируются backend settings. Некоторые CUDA kernels могут давать отличия между запусками или окружениями.

**Исправление:** при необходимости строгой повторяемости включить `torch.use_deterministic_algorithms(True)`, настроить cuDNN и документировать возможную потерю производительности. Для production полезно логировать версии Python, PyTorch, CUDA, NumPy и hashes checkpoint-файлов.

### PORT-001 — жёсткая привязка к Kaggle и побочные эффекты импорта

**Строки:** 22–49, 168–192.

- `DEVICE = select_device()` выполняется при импорте и печатает в stdout.
- Переменные окружения парсятся при импорте, что усложняет тестирование и программное использование.
- Dataset ищется только в `/kaggle/input`.
- Default output — `/kaggle/working`.
- При `USE_RL=1` отсутствие RL-checkpoint полностью останавливает запуск, хотя RL выглядит как опциональный refinement.

**Исправление:** перенести построение config/device в `main()`, добавить CLI/dataclass config и явные пути. Для опционального RL либо делать понятный fallback с warning, либо объявить checkpoint обязательным и валидировать его до загрузки остальных моделей.

## Минимальный набор regression-тестов

1. `optimize_layout()` никогда не возвращает objective ниже входного, если функция заявляет возврат best-so-far.
2. Список имён в `submission.zip` в точности равен списку текущих test-файлов.
3. `load_tiles()` отклоняет любую форму, отличную от `(GRID*TILE, GRID*TILE, 3)`.
4. Resolver выбирает максимальный epoch только внутри заданного model directory.
5. `RL_PROPOSALS` проверяется на `0`, `1`, отрицательное значение и значение больше числа уникальных пар.
6. Heuristic normalization не производит `NaN` при одном или одинаковых значениях.
7. RL-кандидат не заменяет baseline при меньшем baseline objective.
8. Feature-schema test создаёт случай, где local scores для `a` и `b` различаются, и проверяет четыре независимых feature slots.
9. Пустые `train/inputs` и `test` завершаются понятной ошибкой, а не `NaN`/пустым архивом.
10. Smoke-тест загрузки полного набора checkpoint-файлов проверяет общий run ID, grid, tile, architecture и diffusion config.

## Итог

Код синтаксически рабочий и основные tensor shapes согласованы, но pipeline пока не защищён от нескольких тихих ошибок. Наиболее вероятные причины неожиданного падения SSIM или некорректного submission — потеря best-so-far в simulated annealing, безусловное применение RL с несовпадающим objective и повторное использование старого содержимого каталога `submission`.
